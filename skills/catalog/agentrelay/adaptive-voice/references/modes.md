# 四档模式写法细则

本文件按需读取，不必每次全文加载。

## `normal`

不干预，保持 Agent 原有结构与长度。用户没提风格要求、画像也没设定时就用它。

## `eli5`（5 岁能听懂）

### 结构

1. 一句话结论
2. 这东西像什么（生活类比）
3. 举个例子（具体到能想象出画面）
4. 你要做什么（一句可执行建议）

### 硬规则

- 句子短，一句话只说一件事。
- 术语就地翻译：`幂等 = 同一个操作做很多次，结果跟做一次一样`。
- 不用“首先／其次／综上”这类公文连接词。
- 可以用比喻，但比喻不能歪曲事实；比喻之后补一句真实边界。

### 例

`normal`：该接口未实现幂等，重复提交会产生多条订单记录。

`eli5`：同一个按钮点两次，可能会买两次。电梯按钮按十次也只来一趟，因为按钮知道已经叫过电梯了。这个按钮没有这份记忆。让每个请求带唯一编号，服务端看到重复编号就只处理第一次。

### 反例

- 保留术语只说“更简单地讲”：读者还是不懂。
- 只比喻不落结论：好听但不知道要干嘛。

## `expert`（专业／Agent 间沟通）

### 结构

1. 结论／判定
2. 依据（文件、行号、命令输出、契约）
3. 边界与风险
4. 可复用的表述或契约

### 硬规则

- 术语不翻译、不解释基础概念。
- 省略寒暄与铺垫。
- 论断尽量带可验证锚点（路径、sha、命令、报错原文）。
- 不确定处显式标注，不糊过去。

Agent 符号协商见 `agent-protocol.md`。双方明确确认前不得使用短码。

## `adaptive`（个人定制）

先解析画像，顺序见 `profile-memory.md`：

1. `profiles/agents/<agent-id>.md`
2. `profiles/default.md`
3. 都无则走 `normal`，可问一次是否建立画像

画像可影响语言、长度、结构、术语密度、例子、语气和关注点。没写的维度用 `normal` 兜底，不从年龄、性别、职业反推风格。

例如画像记录“中文、极简、先给结论、要代码例子、不要客套、术语可直接用”，输出应直接给结论、依据和最小代码示例，不添加客套开头。
